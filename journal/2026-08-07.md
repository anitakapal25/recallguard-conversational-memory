# Engineering Journal — 2026-08-07

## Session Focus

Implementation and validation of Deliverable 6 for the RecallGuard Conversational Memory System.

The main focus was completing the remaining engineering components around persistent memory storage, retrieval, ranking, context construction, reflection, authentication, logging, API integration, and testing.

---

## 1. Observation

The project required a complete memory pipeline rather than only a vector database.

The required flow was:

```text
User Request
     ↓
Authentication
     ↓
Memory Store
     ↓
Retrieval
     ↓
Ranking
     ↓
Context Builder
     ↓
Reflection / Maintenance
     ↓
Logging
```

ChromaDB was selected as the persistent vector store, while application-level modules were kept separate from the database implementation.

---

## 2. Memory Store Implementation

The `MemoryStore` was implemented around ChromaDB.

The store supports:

* Adding memories
* Semantic retrieval
* Getting a memory by ID
* Listing user memories
* Soft deletion
* Updating memories
* Duplicate detection
* Memory expiration
* Filtering memories by type

Each stored memory contains metadata including:

```text
user_id
memory_type
importance
confidence
created_at
deleted
```

### Decision

The application should interact with ChromaDB through `MemoryStore` rather than directly accessing the collection from every module.

### Reason

This creates a clear persistence boundary and makes the rest of the system easier to test and change.

---

## 3. Retrieval Implementation

`retrieval.py` was implemented as a separate retrieval layer.

The retriever:

1. Converts the query into an embedding.
2. Searches ChromaDB through `MemoryStore`.
3. Applies memory-type filtering.
4. Applies confidence filtering.
5. Removes deleted memories.
6. Converts ChromaDB results into application-level memory dictionaries.
7. Sorts results by similarity.

Specialized retrieval methods were added:

```text
retrieve_preferences()
retrieve_facts()
retrieve_tasks()
```

This kept retrieval logic separate from storage logic.

## 4. Testing Failure: Confidence Filtering

One of the important failures occurred in:

```text
test_confidence_filter
```

The test expected:

```text
min_confidence = 0.5
```

to exclude a memory with:

```text
confidence = 0.20
```

However, the retriever returned five unrelated memories with confidence `0.9`.

### Observation

The test collection was persistent and reused data from previous test executions.

The failure output showed multiple older memories belonging to the same test user.

### Inference

The retrieval filtering logic itself was not the only problem. Test isolation was also important.

The test fixture was updated to create a unique ChromaDB collection for each test run:

```python
MemoryStore(
    collection_name=f"test_{uuid.uuid4().hex}"
)
```

### Result

This prevented stale test data from previous runs from affecting retrieval tests.

---

## 5. Testing Failure: User Isolation

Another failure occurred in:

```text
test_user_isolation
```

The requirement was that memories belonging to another user must never be returned.

The store was therefore updated so retrieval applies the user filter directly at the ChromaDB query level:

```python
where={
    "$and": [
        {"user_id": user_id},
        {"deleted": False},
    ]
}
```

### Decision

User isolation should happen inside the persistence query rather than relying only on filtering after retrieval.

### Reason

Filtering at the database boundary reduces the possibility of accidentally exposing another user's memory to higher layers.

## 6. Collection Abstraction

`MemoryStore` was changed to use:

```python
self.collection
```

instead of a shared global collection.

The constructor obtains the requested ChromaDB collection through:

```python
get_collection(collection_name)
```

### Result

This allowed tests to create independent collections while the production application can continue using the default collection.

This was an important improvement for test isolation and modularity.

---

## 7. Reflection Implementation

`reflection.py` was implemented for background memory maintenance.

Reflection supports:

* Memory summaries
* Expiring old memories
* Removing duplicate memories
* Removing low-confidence memories

An implementation error occurred where the constructor referenced:

```python
collection
```

although only:

```python
get_collection
```

was imported.

### Fix

The reflection engine was changed to obtain its collection through the database abstraction.

The issue reinforced the importance of avoiding undeclared global dependencies.

## 8. Authentication

An API-key-based authentication layer was implemented.

The system supports:

```text
X-API-Key
```

Authentication distinguishes between:

```text
admin
user
```

Two decorators were introduced:

```text
login_required
admin_required
```

The authenticated user's identity is attached to the Flask request:

```python
request.user
```

This identity is then used by the memory endpoints.

## 14. Engineering Decisions

The major decisions made during this session were:

### ChromaDB

Use ChromaDB for persistent vector storage and metadata filtering.

### MemoryStore abstraction

Keep ChromaDB access behind `MemoryStore`.

### User isolation

Apply `user_id` filtering directly during vector retrieval.

### Test isolation

Use independent ChromaDB collections for tests.

### Retrieval separation

Keep embedding generation and retrieval policy in `MemoryRetriever` rather than mixing them into the database layer.

### Reflection separation

Keep maintenance operations in `ReflectionEngine`.

### API authentication

Require API keys before accessing user memory endpoints.

## 15. Checkpoint Reflection

The main lesson from this session was that implementing the individual modules was not enough.

The system had to be validated as an integrated pipeline.

Several failures initially looked like retrieval bugs but were actually caused by:

* Persistent test data
* Shared collections
* Missing user-level isolation
* Incorrect dependency references
* Missing Python dependencies

The debugging process demonstrated the importance of separating:

```text
Observation
    ↓
Inference
    ↓
Decision
    ↓
Verification
```

rather than immediately rewriting implementation code whenever a test fails.
