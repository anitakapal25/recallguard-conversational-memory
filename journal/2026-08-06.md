# Engineering Journal — 2026-08-06

## Session focus
Deliverable 6 architecture and persistent conversational-memory implementation.

## Observation
The project needed a persistent vector-memory layer. Earlier work had used a vector database approach, and the implementation needed reliable storage, retrieval, filtering, and testability.

## Alternatives considered
1. **FAISS** — strong local vector similarity search, but persistence and metadata filtering would require additional application-level storage.
2. **ChromaDB** — provides persistent collections, embeddings, metadata, and filtered queries in one component.
3. **Pure relational storage** — useful for structured metadata, but not sufficient by itself for semantic vector retrieval.

## Inference
Because the project needs semantic retrieval plus metadata filters such as user identity, memory type, confidence, and deletion state, ChromaDB gives a simpler implementation boundary.

## Decision
Use **ChromaDB as the persistent vector store** and keep the application-level `MemoryStore` as the abstraction around it.

## Result
The memory store was implemented around a ChromaDB collection. The design was kept modular so retrieval and reflection do not depend directly on ChromaDB internals.

## Failure / debugging note
An early implementation expected `DATABASE_PATH` from `config.py`, but the project configuration was based on `CHROMA_DB_PATH`. The import mismatch was identified and the store was aligned with the ChromaDB configuration.

## Checkpoint reflection
The main lesson from this session was to keep the storage abstraction stable while changing the underlying vector database. This reduced the number of modules that needed to know about persistence details.
